### 去掉「平台设备id」

页面按**配置名称**识别这一项：把 `configContent` 与 `configKey` 去掉空格、下划线、冒号和连字符
后转小写，命中 `平台设备id` / `platformdeviceid` / `platdeviceid` 三种写法之一即视为平台设备 ID。
命中的项**同时从展示列表和 `setConfigDataEdit` 的提交负载里排除**——只藏不排除的话，隐藏字段
仍会被原样回传，等于界面上删了、保存时又写回去。

## 关键决策

1. **用配置名称识别，不用 `configType`。** 旧版页面里 `configType === 1` 是平台设备 ID
   （多行输入、逗号分隔）、`configType === 2` 是平台邮箱，但当前 Swagger 的
   `ConfigDataEditApiOutput` 只把 `configType` 描述成「系统配置类型枚举」，没有公开枚举含义。
   按类型过滤会连带误杀后端以后新增的同类型配置项，按名称过滤只命中这一条。
2. **恢复的是 2026-09-08 删除前那一版页面**（标签取 `configContent`、邮箱校验按名称触发），
   不是更早那版把「平台邮箱 / 平台设备id」写死在 placeholder、用表单下标判断校验的实现。
3. **菜单脚本节点原样恢复，没有加 `aliases`。** 脚本的 `findMatchingChild` 只对分组节点
   （`appCode === '#'`）用 `[appName, ...aliases]` 查重，像「基础信息配置」这种带真实
   `appCode` 的节点一律按 `appCode`（含 `legacyCodes`）查重，加了别名也不会生效。

## 未完成项与风险

1. **后台那条菜单行可能已经被人工删掉。** 2026-09-08 的记录里把「后台残留菜单行需要人工清理」
   列为待办，是否执行过无法从仓库判断。恢复前端路由后：菜单行还在 → 左侧菜单直接恢复显示
   （2026-09-09 的侧栏过滤会重新放行它，因为本地路由又存在了）；菜单行已删 → 需要重新跑
   `npm run menu:sync:checklist`（先只读预览，再 `--apply`），非管理员角色还要重新绑定权限并重新登录。
2. **`--update` 会改名。** 若后台那条菜单当前叫「系统配置」而不是脚本声明的「基础信息配置」，
   跑 `--apply --update` 会把它改成后者。只想补齐缺失节点就别带 `--update`。
3. **名称识别的覆盖面。** 后端若把这一项的 `configContent` / `configKey` 配成上述三种以外的写法，
   页面会照常把它显示出来，需要把新写法补进 `platformDeviceIdNames`。
4. **被排除的项不会回传。** 这依赖 `setConfigDataEdit` 按传入的 `configType` / `configKey` 逐条更新；
   如果后端实际是「全量替换」语义，不回传会把平台设备 ID 清空。接口文档没有写明更新语义，
   真实登录态下首次保存后应回查一次该配置是否还在。
5. 图标 `ums-config` 在 `src/icons/svg/` 里没有对应文件（路由恢复的是删除前的原值，AI 配置页也用同一个）；
   不影响渲染，只是菜单前没有图标。
